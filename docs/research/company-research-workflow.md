# 按公司深挖的收录流程
框架完成后，按叠纸 → 友谊时光 → 乐元素 → 灵犀推进；每家完成记录再换下一家。
“挖干净”指公开来源已逐项检查，未找到的项目记录缺口，不代表私人信息或全部员工已收全。

每家公司记录：
- 官网产品和历程：列出所有重点女性向产品，标收录、待核实、排除原因。
- 每个项目：制作人、执行制作人、主策、核心策划、主美、核心美术、编剧、音乐，逐岗记录公开署名或“未找到”。
- 每段履历：独立 sources；status 为 active/departed/unknown。active 必须有 checkedAt 和支持在任的来源。
- dateBasis：employment 为真实任职起点，public-observation 为公开亮相日期，unknown 为沿用待核日期。
- checkedAt 只在实际核对原文后填，旧资料迁移不自动写今天。
- 流动：项目调动与离开公司分别核实，不把结束项目当成公司离职；去向无来源留空。
- 来源不支持时撤回断言；百科和媒体是线索，优先官方、采访、署名。
- 搜索过的关键词、来源链接、仍未找到的岗位写入研究日志，避免自动化重复检索。
- 不采集私人联系方式，不发送招聘联系。
- 完成 npm test、npm run check、npx astro build 后形成公司完成报告。
公众号必查：按 [微信公众号接入流程](wechat-channel.md) 搜官方账号、产品公告、研发访谈和招聘；保留原文/转载及读取状态，未核对原文不标已查。

## 微信公众号纳入每轮深挖（2026-10-13用户确认）

- 每家公司都查公众号渠道，优先游戏葡萄、游戏新知、游戏那点事/手游那点事、游戏茶馆、GameLook，以及可确认身份的公司/产品官方号。按公司、产品、工作室和关键人物组合搜索；不同卷均适用。
- 从搜索或可信转载反查真实微信文章链接，优先复用知识库 `server/knowledge/web.mjs` 的 `fetchPublicPage` 读取。易娱7篇原文两轮成功的样本见 [渠道验收](eyu-wechat-validation-2026-10-13.md)。独立工具读取失败时，不能直接认定原文不可读。
- 分开保存原文账号、作者、原文日期、转载日期、链接、核查日和读取状态；取得正文与事实核实是两回事。遇验证/登录阻断记录缺口。
- 读到后必须逐条对照现有档案：有效新事实整合到公司/产品/人员/财务相应位置，重复事实补来源，弱线索记待核实。渠道验证或研究日志不能替代档案整合；尚未入档时明确说明。
- 媒体估算保留估算与平台/地区/期间口径；被投团队不视为公司在职团队。公开页面只存事实摘要和来源链接，全文留内部。
- 每批交付分别报告“读到什么、核实什么、已整合什么、仍有什么缺口”。不把已知URL的小样本成功称为全量检索或长期稳定。

## 跨品类公司与人员归属（2026-10-13用户确认，适用于所有公司）

- 公司档案呈现完整业务与产品目录，不能因收录入口是SLG、女性向或休闲卷，就将公司定义为单一品类公司。每家检索都检查其他品类代表作和对应工作室。
- 编年史分卷归属由具体作品决定；不适合现有卷的作品也可进入公司完整目录（显式 chronicles: []），不能为了收录强行归入某卷。
- 分开判断公司、工作室、产品、人员。公司做SLG不意味着其RPG工作室或员工有SLG经历；发行过某品类也不意味着具备该品类自研团队。
- 人员专业方向根据公开项目署名和岗位履历记录；有明确专业方向的公司/工作室职务使用 specialties，避免自动计入其他品类人才。公司完整人才地图保留跨品类项目关系，分卷人才统计只计对应关系。
- 对明确的RPG/MMORPG制作人，先关联其实际作品，不因缺少SLG经历而反复猜测、追挂SLG项目。无明确项目的人员保持未知，不默认归入公司主打品类。
- 每批验收检查：公司简介是否单一化、非本卷产品是否遗漏、公司/工作室职务是否误传品类、分卷人员统计是否误计、项目制作人是否关联正确。易娱修正及 tests/cross-genre-company.test.ts 为回归样本；适用于所有后续公司mapping。

## 组织架构区（2026-10-14用户新增，适用于所有公司）

- 公司档案新增 orgUnits 内容区并在公司页「组织架构」展示：事业群、工作室群、工作室、项目组、中台、发行品牌、分支机构、子公司/法人。检索中了解到组织架构即收集，腾讯、网易等大厂外部资料较多，优先利用。
- 每个单元必须有能点开的来源；observedAt 记来源口径时间（架构会变动，不写观察日等于宣告永久有效）。parentUnit 表达层级（如工作室隶属子公司），名称与来源原文一致，不自创译名或简称。
- 传闻不入架构（如灵犀"五大自研工作室+九游/交易猫打包"的6月传闻未核，不收）；架构单元与产品归属分开判断，不因某工作室研发某产品就反推整群职责；科普类来源注明口径年份。

## 信息校准轮（2026-10-14用户新增，长期机制）

- 背景：詹钟晖（叮当）案例——公司档案与事件已记 2024-03 管理层交接（饼叔接任），但人物条目仍停在 status:unknown 未记离任，页面上呈现"在职"，与同一档案内的事实矛盾。用户指出：叮当退出/离职的公开信息已经很多，矛盾不该留存。
- 规则一（矛盾即修）：每一轮深挖结束前，把本轮触及公司的人物条目状态与公司时间轴事件对照；发现"事件已记交接/离职/关停而人物未同步"的，当轮修正，不留给下轮。
- 规则二（状态口径）：status:unknown 只能表示"公开信息不足"，不能当"在职"默认值用；有离任事件来源的必须写 to+departed；active 必须有当期来源+checkedAt（schema 已强制）。
- 规则三（定期全量审计）：按批次跑人物状态审计（列出全部非 departed 角色，与公司事件对照）。2026-10-14 首次全量审计 86 条，实质矛盾仅叮当一条，已修；其余为快照观察口径，无冲突。
- 规则四（线索驱动的校准）：用户或渠道（如小红书）指出某人物动态信息量变大时，优先做该人物的校准轮：查到什么改什么，查不到的写进 gaps，不猜测。

## 双循环 mapping（2026-10-15用户新增，详见[发现协议](discovery-protocol.md)）

- 既有循环A（公司→产品）之外，新增循环B（渠道→产品→公司）：每月小游戏月榜/App Store品类榜/TapTap新游榜反向扫描，发现的产品反查归属，新厂商当日进 mapping-plan 仅列名。
- 负面结论四步纪律：≥2检索公式+引擎轮换（搜狗反爬即换内置搜索）+商店开发者账号反查+近三月榜单核查，未完成不得写 not-found。
- 人物离职/新公司事件触发三连查：工商+商标+招聘。
